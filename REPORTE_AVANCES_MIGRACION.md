## 2. Auditoría del Código y Firestore Actual (Paso 3 del Plan)

Al inspeccionar el repositorio se identificó una ventaja arquitectónica clave:

1. **Capa de datos centralizada (`src/api/dataClient.js`):**
   Ninguna de las pantallas de React (`CaseList.jsx`, `CaseEditor.jsx`, `CaseSession.jsx`, `StudentCases.jsx`, `Reports.jsx`, `UserManagement.jsx`) invoca funciones de Firestore directamente. Todas consumen `dataClient.entities`:
   * `ClinicalCase`
   * `StudentResult`
   * `User`
   * `PendingUser`
   * `StudentAccount`
2. **Colecciones actuales en Firestore y redundancias detectadas:**
   * `users`, `pending_users` y `student_accounts` almacenan información de usuarios e invitaciones por correo de forma separada en Firestore.
   * `clinical_cases` almacena los casos clínicos con un arreglo anidado `questions: []`.
   * `student_results` almacena los intentos de los alumnos con un arreglo anidado `answers: []`.
3. **Reglas de seguridad (`firestore.rules`):**
   * Definen dos roles operativos principales (`admin` para docentes y `student` / `user` para alumnos), validando estado activo (`is_active != false`) y restringiendo a los alumnos a leer únicamente casos con `status == "published"` y sus propios resultados.

## 3. Diseño e Implementación del Esquema Relacional (Pasos 5 y 6 del Plan)

### 3.1 ¿Por qué PostgreSQL en lugar de MySQL?
* **Supabase opera exclusivamente sobre PostgreSQL:** Aunque el archivo `Diagrama_ER.mwb` se diseñó originalmente en MySQL Workbench, Supabase utiliza PostgreSQL como motor relacional y genera automáticamente sobre él la API REST (`@supabase/supabase-js`) y la seguridad a nivel de fila (**RLS**), evitando tener que programar y alojar un servidor backend intermedio (Node/Express) desde cero.
* **Adaptación limpia de tipos de datos:** Se conservaron exactamente las **5 tablas y nombres en español** del `Diagrama_ER.png`, adaptando únicamente los tipos propios de MySQL a tipos nativos de PostgreSQL:
  * `TINYINT` $\rightarrow$ `BOOLEAN`
  * `DATETIME` / `TIMESTAMP` $\rightarrow$ `TIMESTAMPTZ`
  * `INT AUTO_INCREMENT` $\rightarrow$ `BIGINT GENERATED BY DEFAULT AS IDENTITY`

### 3.2 Diccionario de Tablas Creadas (`supabase/migrations/20261021000100_esquema_relacional_pulselab.sql`)

| Tabla en PostgreSQL | Propósito y Mapeo desde Firestore | Clave Primaria (PK) | Claves Foráneas (FK) y Restricciones Clave |
| :--- | :--- | :--- | :--- |
| **`public.usuario`** | Unifica `users`, `pending_users` y `student_accounts` en una sola entidad relacional. | `id_usuario` | `correo UNIQUE NOT NULL`<br>`CHECK (rol IN ('admin', 'student', 'user'))`<br>`auth_uid UUID UNIQUE` / `firebase_uid VARCHAR(128) UNIQUE` |
| **`public.caso_clinico`** | Datos generales del caso y signos vitales base (`fc`, `fr`, `spo2`, `pa_sistolica`, `pa_diastolica`, `temperatura`, `imc`). | `id_caso_clinico` | `usuario_id_usuario` $\rightarrow$ `usuario(id_usuario) ON DELETE SET NULL`<br>`CHECK (estado IN ('draft', 'published'))`<br>`legacy_firebase_id UNIQUE` |
| **`public.pregunta`** | Desglosa el arreglo `questions[]` de cada caso clínico en filas individuales (relación `1:N`). | `id_pregunta` | `caso_clinico_id_caso_clinico` $\rightarrow$ `caso_clinico(id_caso_clinico) ON DELETE CASCADE`<br>`CHECK (LOWER(opcion_correcta) IN ('a','b','c','d'))`<br>`UNIQUE (caso_clinico_id_caso_clinico, orden)` |
| **`public.resultado`** | Encabezado de cada intento completado por un alumno (`aciertos`, `porcentaje`, `tiempo_usado_segundos`, `comodin_usado`). | `id_resultado` | `usuario_id_usuario` $\rightarrow$ `usuario(id_usuario) ON DELETE CASCADE`<br>`caso_clinico_id_caso_clinico` $\rightarrow$ `caso_clinico(id_caso_clinico) ON DELETE CASCADE`<br>`legacy_firebase_id UNIQUE` |
| **`public.respuesta_alumno`** | Desglosa el arreglo `answers[]` de cada intento para análisis individual por pregunta. | `id_respuesta_alumno` | `resultado_id_resultado` $\rightarrow$ `resultado(id_resultado) ON DELETE CASCADE`<br>`pregunta_id_pregunta` $\rightarrow$ `pregunta(id_pregunta) ON DELETE CASCADE`<br>`UNIQUE (resultado_id_resultado, pregunta_id_pregunta)` |

## 4. Seguridad Row Level Security — RLS (Paso 9 del Plan)

En `supabase/migrations/20261021000200_politicas_rls.sql` se habilitaron las políticas RLS en las 5 tablas replicando la lógica de `firestore.rules`:

* **Funciones auxiliares SQL:**
  * `public.current_user_email()`: Extrae el correo electrónico del token JWT de la sesión activa.
  * `public.is_admin()`: Verifica si el usuario autenticado tiene `rol = 'admin'` y `activo = TRUE` en `public.usuario` (o es el correo administrador semilla).
  * `public.is_active_user()`: Verifica si el usuario está registrado y activo en `public.usuario`.
* **Políticas aplicadas:**
  * `usuario`: Un alumno solo puede leer su propio perfil y no puede escalar su propio `rol` a `admin` ni cambiar su campo `activo`. Solo un `admin` puede listar, pre-registrar, activar/desactivar o eliminar usuarios.
  * `caso_clinico` y `pregunta`: Los alumnos activos solo pueden hacer `SELECT` sobre casos con `estado = 'published'` y sus preguntas asociadas. Solo `admin` puede crear, editar o borrar casos y preguntas.
  * `resultado` y `respuesta_alumno`: Los alumnos activos solo pueden insertar y leer sus propios resultados y respuestas. Los docentes (`admin`) pueden consultar todos los resultados para la pantalla de Reportes.

## 5. Pruebas Locales de Integridad y Migración (Pasos 7 y 11 del Plan)

Se configuró un entorno de pruebas SQL local ejecutable con Node.js (`scripts/test-local-db.js` y `scripts/migrate-firestore-to-postgres.js`) que valida el esquema antes de tocar datos reales:

### 5.1 Resultados de `npm run db:test` (`scripts/test-local-db.js`)
1. **Aplicación de migraciones y `seed.sql`:** Creó sin errores las 5 tablas, políticas RLS y datos semilla (1 docente, 2 alumnos, 1 caso clínico con 2 preguntas y 1 intento con 2 respuestas).
2. **Prueba 1 (FK `pregunta` $\rightarrow$ `caso_clinico`):** Confirmado que PostgreSQL rechaza insertar preguntas que apunten a un `id_caso_clinico` inexistente.
3. **Prueba 2 (FK `resultado` $\rightarrow$ `usuario` / `caso_clinico`):** Confirmado que PostgreSQL rechaza guardar resultados con alumnos o casos inexistentes.
4. **Prueba 3 (`CHECK` en `usuario.rol`):** Confirmado que PostgreSQL rechaza roles fuera de `('admin', 'student', 'user')`.
5. **Prueba 4 y 5 (Consultas `JOIN`):** Verificado que las consultas relacionales entre `caso_clinico` + `pregunta` y `resultado` + `usuario` + `respuesta_alumno` devuelven los conteos, promedios y detalles exactos que requiere el frontend.

### 5.2 Script de Migración (`npm run db:migrate` — `scripts/migrate-firestore-to-postgres.js`)
* Lee un respaldo JSON de las colecciones de Firestore (`users`, `pending_users`, `student_accounts`, `clinical_cases`, `student_results`).
* Unifica los usuarios por correo sin duplicarlos (`ON CONFLICT (correo) DO UPDATE`).
* Conserva la trazabilidad guardando el ID original de Firestore en `legacy_firebase_id` y resuelve automáticamente las llaves foráneas (`id_usuario`, `id_caso_clinico`, `id_pregunta`, `id_resultado`).

## 7. Integración Incremental con React (Paso 10 del Plan)

Para conectar React sin reescribir los componentes visuales existentes:

1. **`src/api/supabaseClient.js`**: Inicializa el cliente oficial `@supabase/supabase-js` leyendo `VITE_SUPABASE_URL` y `VITE_SUPABASE_PUBLISHABLE_KEY`.
2. **`src/api/supabaseAdapter.js`**: Implementa los métodos `list`, `get`, `filter`, `create`, `update` y `delete` para `ClinicalCase`, `StudentResult`, `User`, `PendingUser` y `StudentAccount`, mapeando de forma transparente los nombres en español de la base de datos (`titulo`, `nombre_paciente`, `pregunta`, `resultado`, `respuesta_alumno`) a las propiedades que esperan las vistas de React (`title`, `patient_name`, `questions`, `answers`).
3. **`src/api/dataClient.js`**: Selecciona automáticamente el adaptador de Supabase cuando las variables `VITE_SUPABASE_*` están presentes, manteniendo Firebase y LocalStorage como respaldo.
4. **`scripts/vite-local-pg-plugin.js`**: Añade soporte de desarrollo local en Vite e incluye un inspector visual en `http://localhost:5173/api/local-pg` para visualizar en vivo las columnas, llaves primarias/foráneas y registros de las 5 tablas.
